## Boundaries

The raw Tennis provider supplies generic `format.regulation.periods: 5` even for ordinary ATP matches, and sample live `situation` contains baseball-style base fields. These fields are not evidence of match points, a five-set format or historical coverage. The collector must retain verified participant/set/status data and disclose missing point-by-point/history coverage.

The alert transport cannot guarantee exactly-once acceptance across a network failure. The implementation will use an atomic claim and favor no duplicate: an ambiguous send is retained as unknown and will not be automatically retried. A definite non-2xx rejection may retry only after fresh eligibility revalidation.

## Implemented corrections

F9: `alert-delivery.js` uses a conditional D1 `pending -> sending` update before delivery. Only the process that changed the row may send. After claiming, it rereads subscription/preferences and then the latest persisted canonical feed immediately before transmission. Eligibility requires current model, live status, a real current rating above the current threshold, a feed no older than 120 seconds, and no partial/invalid/rejected/stale evidence. The original queued crossing also expires after 120 seconds. Missing canonical data cancels the claim. Archived snapshots and stale queued scores are no longer fallback recommendations. The notification's title/body come from the current eligible game. `/health` reports notification version `2026-11-01.canonical-revalidation.1` and the active safeguards.

The existing `alerts.status` text column supports owner-qualified `sending:<UUID>`, `cancelled`, `sent`, and `delivery_unknown`; no schema migration is needed. A definite HTTP rejection can return to pending, then must pass all gates again. Ambiguous transport failure, an invalid transport result, or acknowledgement failure after sending leaves a terminal unknown record. A crash during transmission leaves the owned sending status, which is not retried. This deliberately favors possible missed delivery over duplicate delivery. Existing retention eventually removes those records. Missing/unreadable canonical data before transmission cancels the row rather than leaving a retry backlog. A cancelled unsent row can be replaced only on a new genuine threshold crossing; sent, sending and unknown rows cannot. Settlement checks both claim owner and original creation time. An invalid old push endpoint cannot delete a replacement subscription registered while that attempt was in flight. Provider/device delays after successful transmission remain outside this server-side guarantee; the existing Web Push TTL is unchanged.

F8: `providers/tennis.js` flattens `events[].groupings[].competitions[]`, keeps individual match IDs and actual match status, deduplicates IDs, and supports existing flat matches. Singles and doubles participant identities are normalized from athlete/roster evidence. Available set winner flags provide set totals; no game-margin inference is used. Missing set history remains missing. Tournament status never turns scheduled matches live. Persisted match scoreboard context supports `/game/Tennis/:id` without calling the observed-unsupported generic summary endpoint. Ingestion excludes Tennis from summary acquisition, avoiding one failing request per newly collected match.

`tennisCoverage` reports available set coverage separately from unverified point-by-point/history coverage and supplies a human-readable reason. Started Tennis ratings remain partial. The API preserves set-game scores, tiebreak scores and available point fields. No unsupported match-point or best-of interpretation was added. Existing card and Game Center participant markup explicitly excludes Tennis from team-page buttons; its Overview tab and scoring table retain keyboard/tab/row-header semantics. Browser visual QA is owned by the main task and is not claimed here.
